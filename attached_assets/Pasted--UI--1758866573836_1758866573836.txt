변경 개요

현재 UI 그대로 유지하면서

접수 신청 테이블에서 선택한 요금제가 **관리자 패널(서비스 플랜)**에 요금제명/데이터/월요금까지 정확히 매핑되도록 처리.

접수 신청 시 간헐적으로 뜨는 “Upload failed with status 400” 토스트 해결.

수정 목적(한 줄)

프론트 로직만 최소 수정으로 요금제-서비스플랜 정보 매칭 및 파일 선택 토스트 회귀 제거.

해결할 오류 / 재현

오류1: 접수 신청 버튼 클릭 시 파일 미첨부임에도 “Upload failed with status 400” 즉시 토스트.

재현: /submit-application → 필수값만 입력 → 버튼 클릭 즉시 토스트(네트워크 요청 생략/4xx 오매핑).

기대: 파일 없이도 200/201로 정상 접수.

오류2: 접수 신청에서 요금제 선택했는데, 관리자 패널의 서비스 플랜에서 명/데이터/월요금 정보가 일치하지 않거나 비어 있음.

재현: 요금제 드롭다운 선택 → 접수 생성 → 관리자 패널 상세 보기.

기대: 요금제명/데이터/월요금 정확히 표시.

변경 범위 요약

프론트엔드만 수정 (로직·매핑·가드).

백엔드/환경변수/DB 스키마/스타일/UI 레이아웃 변경 없음.

(백엔드 라우트는 현행 유지, 필요 시 “코드 수정 없이” 보완 제안만)

수정 파일 목록 (+ 이유)

client/src/pages/SubmitApplication.tsx

이유: onPlanSelect/onSubmit 로직에서 요금제 코드/정보 전달 정합성 보장, 파일 미첨부 가드 제거/수정.

client/src/components/PlanSelect*.{tsx|jsx} (실제 경로)

이유: 선택 항목 객체 구조 정규화 → { code, name, data, monthlyFee } 일관 제공.

client/src/pages/AdminPanel*.{tsx|jsx} or client/src/pages/ReceptionList*.{tsx|jsx}

이유: 표시 시점에 코드→정보 매핑 수행(렌더 시 조회 or 캐시 맵 활용)으로 명/데이터/월요금 표출.

(필요 시) client/src/lib/errorMapper.ts / client/src/lib/upload*.ts

이유: FILE_REQUIRED 오인 토스트 분기 제거 및 FormData 생성시 file 없으면 append 생략.

예상 변경 내용 (요약 diff)

[추가] 요금제 객체 표준화

드롭다운 아이템: { code, name, data, monthlyFee }

선택 시 form.planCode = code 로 저장(= DB 스키마 불변).

[치환] 관리자 패널 표시 로직

저장된 planCode로 표시 시점에 매핑:

1순위: 클라이언트 캐시 맵(요금제 카탈로그)에서 code→{name,data,monthlyFee} 매칭

2순위: /api/service-plans/:code 조회(백엔드 라우트 신규 추가 없이 기존 검색 API 사용 가능 시 그걸 사용)

화면엔 name/data/monthlyFee 렌더 (UI 구조/클래스 그대로)

[삭제] 파일 미첨부 강제 토스트 분기

if (!file) { toast('파일을 선택…'); return; } 제거

공통 에러 매퍼가 4xx를 FILE_REQUIRED로 오인 매핑하는 분기 제거/가드

[치환] FormData 구성

if (file) formData.append('file', file)

파일 없으면 append 생략 + 요청 진행

[유지] 버튼/레이아웃/Tailwind/HTML, 환경/DB/스키마 그대로 유지

리스크와 회피책

리스크: 공통 에러 매퍼 수정 시 다른 페이지 토스트에 영향

회피: SubmitApplication 전용 핸들러로 범위 한정, 공통 분기는 최소 변경

리스크: 매핑 실패 시 빈값 표시

회피: 캐시 맵 1차, API 조회 2차, 그래도 실패 시 원래 code 표기 + “정보 준비중” 뱃지(UI 구조·스타일 불변)

롤백 계획

프론트 수정 단일 커밋 묶음 → 이상 시 git revert <commit> 즉시 복귀

캐시 맵/표시 로직 변경은 기존 분기 보존하여 빠른 원복

검증 시나리오 & 성공 기준

접수(파일 없음)

필수값만 입력 → 요청 전송 확인, 응답 200/201, “파일 선택” 토스트 미표출

접수(파일 있음)

1MB 미만 파일 첨부 → 200/201, 파일 메타 저장

요금제 매핑(목적 기능)

접수 시 planCode 저장 → 관리자 패널에서 동일 접수 상세 열람 시

요금제명/데이터/월요금 정확히 표시(코드→정보 매핑 성공)

회귀 방지

개통 드롭다운 검색/선택/제출 정상 (콘솔 에러 0)

/completed 페이지 흰 화면 없음(에러 경계/빈 데이터 가드)

동등성

개발/운영 동일 커밋 배포 후 위 1)~4) 동일 결과

⚠️ UI/스타일/컴포넌트 구조/환경변수/DB 스키마 변경 없음을 명시합니다.

참고(백엔드 변경 없이 요금제 매핑을 하는 방식)

DB 스키마 불변을 위해 planCode만 저장하고,

표시 시점(관리자 패널)에서 코드→정보를 매칭합니다.

기존에 요금제 카탈로그를 불러오는 API가 있다면 그것으로 맵을 구성하고, 없으면 클라이언트 캐시(초기 데이터 페치 결과)로 1차 사용, 실패 시 기존 검색 API로 2차 조회합니다.

이렇게 하면 데이터 정합성 확보 + 스키마/백엔드 무변경을 동시에 만족합니다.
