2) 상세 요구사항
A. 접수 관리(딜러) – 통신사 선택 시 접점코드 자동 매칭

기존 접두어 로직(통신사별 ‘L프/KT…’ 등) 은 유지하되, 자동 매칭된 코드가 우선 적용되도록 처리

A-1) 일반 접수 생성 (통신사/접점 포함)

POST /api/documents

{
  "customerName": "홍길동",
  "customerPhone": "01012345678",
  "carrier": "선불)프리티LG",
  "contactCode": "L프742813",
  "storeName": "민스마트정석", 
  "customerType": "new",             // "new" | "port-in"
  "activationStatus": "대기",        // 생성 시 항상 "대기"

  "uploadedAt": "2025-11-06T03:12:00Z"
}


성공 응답

{
  "success": true,
  "document": { "id": 18421, "activationStatus": "대기" }
}

A-2) “기타 접수” 생성 (기타신청 → 접수 관리 등록)

POST /api/documents

{
  "customerName": "테스트",
  "customerPhone": "01000000000",
  "carrier": "후불)미디어",
  "contactCode": "M123456",          
  "storeName": "민스마트정석",
  "activationStatus": "대기",
  "notes": "{\"type\":\"etc\",\"source\":\"etc-application\",\"memo\":\"유심 재발송 요청\"}"
}


성공 응답

{ "success": true, "document": { "id": 18422, "activationStatus": "대기" } }


규칙

생성 시 activationStatus는 무조건 "대기".

storeName은 세션의 판매점명 자동 주입(프론트에서 잠금).

contactCode는 자동매칭 값이 있으면 그 값 우선, 없으면 수동 입력 허용.

부록 B. 접점코드 자동매칭 API 사양

GET /api/contact-codes/auto-match?carrier={carrier}
권한: 딜러 세션만 허용 (user.dealerId 존재)

요청 예
/api/contact-codes/auto-match?carrier=선불)프리티LG

동작 규칙 (우선순위)

세션의 dealerName 과 쿼리 carrier 일치

isActive = true (컬럼 존재 시)

ORDER BY updatedAt DESC → 최신 1건 반환

응답 (성공)
{
  "success": true,
  "result": {
    "code": "L프742813",
    "dealerName": "민스마트정석",
    "carrier": "선불)프리티LG",
    "id": 90231,
    "updatedAt": "2025-11-05T10:20:00Z"
  }
}

응답 (매칭 없음)
{ "success": true, "result": null }

응답 (권한 오류)
{ "success": false, "error": "dealer-only" }

서버 조회(의사 SQL)
SELECT *
FROM contact_codes
WHERE dealer_name = :dealerName
  AND carrier     = :carrier
  AND (is_active IS NULL OR is_active = TRUE)
ORDER BY updated_at DESC
LIMIT 1;

부록 C. 접점코드(접두어) 처리 규칙

자동매칭이 성공하면 반환된 code 문자열을 그대로 사용(접두어/형식 보정 금지).

자동매칭이 없을 때만 기존 접두어 보조 로직 적용 가능 (UI 안내 + 수동 입력 허용).

(참고용) 과거 접두어 예:

선불)프리티LG → L프

후불)KT → K

선불)프리티SK → S프

단, 최종 저장 값은 사용자가 입력/자동매칭된 실제 접점코드 그대로 저장.
