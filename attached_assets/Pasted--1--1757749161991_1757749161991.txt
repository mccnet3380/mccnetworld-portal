너는 내 리포지토리의 코드 수정 전담 개발자다. 아래 조건을 반드시 지켜라.

[상황 요약]
- 화면: “개통완료 관리(목록/상세/수정)” 영역.
- 요구사항:
  1) 개통완료 목록에서 '요금제' 입력/선택 UI가 단순 텍스트임. “접수신청” 화면에서 쓰는 요금제 검색 기능(통신사별 필터 + 검색)이 동일하게 동작해야 한다.
  2) “개통취소” 버튼 클릭 시, 별도 ‘개통취소 카테고리’로 이동시키지 말고, **개통완료 테이블의 ‘개통취소일’ 컬럼**에 버튼 클릭 시각을 저장하여 취소 처리하라.
  3) “고객 정보 수정” 모달에서 저장 시 **‘정보 수정 실패’** 토스트가 발생한다. 원인을 찾아 **실제 저장이 되도록** 수정하라.
  4) 모든 토스트 메시지 노출시간을 **3초(3000ms)** 로 통일하라.

[금지 및 원칙 — 매우 중요]
1) **오류가 발생한 부분만 수정**하라.
2) **UI(레이아웃/디자인/스타일/컴포넌트 구조)는 절대 수정 금지.**
   - 버튼 색상, CSS, Tailwind 클래스, HTML 구조 변경 금지.
3) **.env, Secrets, DB 연결 설정, 운영 DB 관련 로직 수정 금지.**
   - 만약 DB 스키마 변경이 필요하면, “코드 수정 없이” 마지막에 ‘DB 스키마 변경 제안’ 섹션으로 설명만 하라.
4) **부분 코드 금지. 실제로 수정된 각 파일은 ‘파일 전체 최종본’만 제출.**
5) 설명은 간단히. 내가 즉시 복붙하여 실행 가능해야 한다.

[구체 작업 지시]
A) “개통완료 목록의 요금제 선택” 기능
- “접수신청” 화면에서 이미 사용 중인 요금제 검색/선택 로직(통신사별 필터링 + 검색)을 **그대로 재사용**하라.
- 재사용 방식 우선순위:
  (1) 공용 컴포넌트(예: PlanSelect, RatePlanSelect 등)가 있다면 **해당 컴포넌트 import만**으로 붙여 넣어라.
  (2) 공용 훅/서비스(예: useRatePlans, fetchRatePlansByCarrier 등)가 있다면 가져다 써라.
  (3) 아무 것도 없다면, “접수신청”에서 쓰는 **동일 API/동일 필터 로직**만 복제해 동작하게 하되, **레이아웃/스타일은 변경하지 말 것**.
- 통신사 변경 시 요금제 목록이 해당 통신사만 보이게 하며, 검색어 입력으로 추가 필터가 되도록 구현.
- 최종 선택 값은 기존 저장 필드(예: servicePlanId, ratePlanId, planName 등)에 **그대로** 반영.

B) “개통취소” 처리 방식 변경
- “개통완료 테이블”의 **개통취소일**(예: canceledAt, cancellationDate 등) 컬럼에 버튼 클릭 시각을 저장.
- 별도 ‘개통취소 카테고리/테이블’로 **이동시키지 말 것**. (기존 이동 로직이 있다면 제거하고 동일 테이블 내 필드 업데이트로 통일)
- 목록 그리드의 “개통취소일” 컬럼에 저장된 값이 즉시 반영되도록 조회 로직을 점검.
- 취소 API(예: POST /api/activations/:id/cancel 또는 동등 라우트)에서 트랜잭션으로 안전하게 업데이트.
- 만약 “개통완료 테이블”에 **취소일 컬럼이 존재하지 않는 경우**, 코드 수정 없이 마지막에 ‘DB 스키마 변경 제안’으로만 기술하라.

C) “정보 수정 실패” 오류 수정
- “고객 정보 수정” 모달 저장 시 실패 토스트가 뜬다. 관련 API(예: PATCH /api/activations/:id, PUT /api/documents/:id 등)를 확인하여, 실제 DB 업데이트가 성공하도록 수정.
- 흔한 원인 점검(정확히 확인하여 필요한 최소 변경만 적용):
  - 라우트/서비스에서 body 검증(zod/Joi) 스키마가 실제 필드명과 불일치
  - 프런트 필드명 ↔ 서버 필드명 매핑 누락(예: ‘요금제명 planName’ vs DB는 ‘servicePlanId’만 받는 구조)
  - 트랜잭션 미사용/오류 swallow, 권한 미들웨어에서 401/403 누락
  - 응답에서 success:true/false 형식 통일 안 됨
- 저장 성공 시 성공 토스트가 뜨고, 그리드가 최신값으로 보이도록(선행되어 있다면 그대로 사용) 보장.

D) 토스트 메시지 노출시간 통일
- 사용하는 토스트 라이브러리(예: react-hot-toast, notistack, antd message 등)의 **전역 기본 duration**을 3000ms로 통일.
- 개별 호출부에서 duration이 상이하게 지정되어 있으면 3000ms로 맞추거나, 공용 wrapper를 쓴다면 wrapper 기본값을 3000ms로 강제.
