4) 예상 변경 내용(요약 diff – 개념)
A) 드롭다운 이중 오픈 방지

통신사 셀렉트 컴포넌트

onFocus + onClick 동시 오픈 → 한 곳으로 통합

open 상태를 단일 소스(state) 로 관리

useEffect 내 carrier 변경 시 open 토글 금지

자동완성 라이브러리 사용 시 onInputChange와 onChange 중복 호출 해제

필요 시 debounce(150~250ms) 적용하여 단 한 번의 호출만 발생

B) 접점코드 자동 매칭

선택된 carrier와 로그인 사용자 컨텍스트의 storeName으로 단건 조회 호출:

예: GET /api/contact-codes?carrier=<carrierKey>&storeName=<encodedStoreName>

응답 성공 시:

접점코드 접두 규칙 적용(기존 로직 유지)

코드 뒤 3~6자리 자동 채움

‘판매점명’(읽기 전용) 자동 채움

응답 실패 시:

토스트 1회만 노출(현재는 선택할 때마다 반복 노출됨 → 1회로 제한)

중복 호출 금지: carrier가 같을 땐 추가 호출 방지(memo/cache)

6) 리스크와 회피책

리스크: 드롭다운 이벤트 제거 시 다른 입력 흐름 영향 가능

회피: 동일 폼 내 다른 셀렉트들과 동일한 제어 패턴 적용, 변경 범위 최소화

리스크: 자동매칭 호출 보정 시 기존 캐싱 영향

회피: carrier + storeName 키 기반의 간단한 in-memory cache(컴포넌트 생애주기 한정)

7) 롤백 계획

수정 전 변경 파일 백업(또는 커밋 tag: revert/submit-autofill-YYYYMMDD)

문제가 발견되면 해당 파일만 원복 → 개발 서버 재시작

8) 검증 시나리오 & 성공 기준(개발 서버 전용)
시나리오 1: 드롭다운 단일 트리거

/submit 진입 → 통신사 입력 포커스

자동완성/드롭다운이 한 번만 열림

항목 선택 시 중복 onChange 없음

성공 기준: 드롭다운 한 번만 열리고 선택 이벤트 중복 0회

시나리오 2: 접점코드 자동 매칭 성공

판매점 계정 로그인(테스트 계정)

통신사 선택

토스트 없이 접점코드/판매점명 자동 채움

성공 기준: 자동매칭 성공 시 토스트 없음, 값 즉시 채워짐

시나리오 3: 접점코드 자동 매칭 실패 (음성 케이스)

존재하지 않는 조합(carrier+storeName) 강제

1회만 경고 토스트 노출

성공 기준: 중복 토스트 미노출, 수동 입력 진행 가능

시나리오 4: 회귀 테스트

기존 다른 셀렉트/자동완성(요금제 등) 정상 동작

제출/검증/임시저장 흐름 영향 없음

9) 제출 규칙

사전 변경 안내 승인 전, 코드 본문 제시 금지

수정 전/후 동일 시나리오 스크린샷 + 콘솔 로그 캡처로 검증 결과 첨부

개발 서버에서만 테스트 완료 후, 제가 확인/승인하면 운영 반영 진행
